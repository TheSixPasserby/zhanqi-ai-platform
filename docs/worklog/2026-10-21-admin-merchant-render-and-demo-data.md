# 管理后台与商户工作台的渲染修复 + 演示数据扩充

- 日期：2026-10-21
- 分支：`fix/admin-merchant-render-and-demo-data`
- 涉及：`static/admin`、`static/merchant`、`assets/js/charts.js`、`db/seed.sql`、`AdminService.java`

## 一、五个模块为什么是空白

用户报的现象是「商品工作台概览 / 7 日走势 / 商品排行 / 营收构成 / 营收统计全空白」。
PC 管理后台的「运营概览」四张图其实也是同样的空白，只是此前没人截图核对过。

根因只有一个，且在两端重复出现：

```js
// 修复前
new Vue({
  components: {
    'tab-home': tabHome,          // 子组件
    'zq-line': window.ZQCharts.LineChart,  // 图表组件也注册在这里
    ...
  }
})
```

Vue 2 的局部 `components` **只对注册它的那个实例的模板可见**。
`tab-home` / `tab-stat` / `view-summary` 都是根实例的子组件，它们的模板里写
`<zq-line>` 时查不到根实例的局部注册，于是标签被当成原生未知元素渲染，
图表区高度为 0 —— 卡片只剩标题。

更麻烦的是 `vendors/vue.min.js` 是**生产版**，不会打印
「Unknown custom element」，所以控制台一片干净，问题被静默吞掉多年。

**修法**：在 `new Vue(...)` 之前用 `Vue.component('zq-line', ...)` 全局注册
（admin.js 与 merchant.js 各一处，共 4 个图表组件）。

### 顺带修掉的两个渲染问题

1. **商家营收排行全是 ¥0**
   `merchantRank` 的字段叫 `revenue`，而 `zq-bars` 默认读 `amount`。
   买家排行之所以正常，是因为前端多做了一层 `buyerItems` 映射。
   修法：`<zq-bars ... value-key="revenue">`。

2. **30 天折线图 X 轴标签叠成一团**
   给 `LineChart` 加了 `labelStep`：点数超过 10 时按 `ceil(n/8)` 抽稀，
   并强制显示最后一个点。这个改动在 `charts.js` 里，三端共用。

## 二、新增商家为什么必然失败

`Accounts.create()` 读 `name` / `shopName` / `shopType`，
而列表与更新接口用的是 `contact` / `short` / `type`。
新增表单提交的是后者，后端读 `name` 得到空串 → 抛「请填写联系人姓名」。

这是**同一份数据在两套接口里用了不同键名**，前端少了一层适配。
修法：在 `accountComponent.save()` 的创建分支做映射，并在提交前做字段级校验，
明确提示「还有一项没填：店铺名称」，而不是等后端返回一句笼统的错误。

顺带：侧边栏「商家管理」用的 `el-icon-shop` 在 Element UI 2.15 里**不存在**
（正确的是 `el-icon-s-shop`），所以图标一直是空的。

## 三、演示数据扩充

`seed.sql` 从 8 点位 / 3 商家 / 2 游客 / 10 商品 / 5 活动 / 16 知识 / 7 订单
扩到 **14 / 6 / 12 / 27 / 10 / 30 / 45**，并补了 26 条打卡记录。

设计要点：

- **订单、打卡、新账号的日期用 `NOW()` / `CURDATE()` 相对生成**。
  写死日期会让「近 7 日走势」在几周后变成一条平线 —— 这正是原来演示效果差的原因。
- 数据之间保持引用一致：订单的 `merchantId` / `productId` / `buyerId` 都能对上，
  金额 = 单价 × 数量，状态分布 pending 4 / confirmed 7 / used 32 / cancelled 2。
- 新增 3 家商户（豆瓣坊、林盘茶舍、竹编铺）与 6 个点位呼应，
  商品、活动、知识库条目也围绕这些新场景写，避免出现「有商品没商家」的孤儿数据。
- 新账号 `loginCount` 仍为 0，保持「登录页初始不展示任何账号」的约定。

## 五、发现但**没有**修的缺陷

**主键会复用，导致新账号继承旧账号的订单。**

`Db.nextId()` 用「行数 + 1」生成序号，只在本表内防撞，不检查订单等外部引用。
实测：删除商家 `m7` 后再新建，又拿到 `m7`，登录后直接看到前一个 m7 的 4 笔历史订单。

试过改用 `information_schema.TABLES.AUTO_INCREMENT`，但 MySQL 8 对它有统计缓存
（`information_schema_stats_expiry` 默认 24 小时），读到的值滞后：
真实值 61、读出来 51，`SET_VAR` 提示对该查询也无效。已回退。

彻底修需要一张独立的序号计数器表（`UPDATE ... SET v=v+1` 原子取号）或改软删除，
属于独立改造，不宜混在本次渲染修复里。**建议单独立项。**

## 六、给后人的提醒

- 三端任何「卡片只有标题、图表区空白、控制台无报错」的现象，先查组件注册方式，
  再看 `valueKey` 是否与数据字段同名。
- 自检脚本里的数量断言与 `seed.sql` 是硬绑定的，扩数据必须同步改，
  但**不要改成 `> 0`** —— 那等于放弃这条断言。
