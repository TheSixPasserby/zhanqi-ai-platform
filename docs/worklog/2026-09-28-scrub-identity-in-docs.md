# 清理文档里可直接照抄的提交身份，并同步已过时的待办

- 日期：2026-09-28
- 作者：Windows 侧 agent（提交身份用操作者本人的 GitHub 账号）
- 分支 / PR：`chore/scrub-identity-in-docs`

## 做了什么、为什么

两件事，都由「远端已经往前走了」触发：

### 1. 本地仓库与远端脱节，先同步

接手时本地 `main` 还停在 `2810af3`，而远端 `main` 已经到 `4fa71ae`（落后 10 个提交）。
这期间发生的事情值得记一笔：

| PR | 内容 | 谁做的 |
| --- | --- | --- |
| #2 | 本机这批工作（迁移 + P0/P1/P2 修复 + `HANDOVER.md`） | 本机 agent |
| #3 | **把「提交必须用本人 GitHub 身份」写进 `AGENTS.md` 第六节**，`agent-memory` 新增「协作」分类 | 仓库属主 |
| #4 | 开启 `main` 分支保护（合并必须走 PR、禁 force push）并记录 | 仓库属主 |

也就是说：本机这边提的那条「身份规则」建议，被对方采纳并正式固化了。
同步动作：把本地 `main` 指到 `4fa71ae`、切过去、删掉已合并的本地分支。

### 2. 按新规则清理自己留下的身份明文

新规则的原话是：

> 照抄别人的 `git config`（**包括文档、工作日志里出现的身份配置示例**）
> 等于把自己的提交记到别人头上——此事真实发生过，靠改写历史才纠正。

而 `HANDOVER.md` 里正留着一条**可直接复制粘贴的完整身份**
（`HANDOVER.md` 的 Git 条目），本机那份 worklog 里也把账号名写进了正文。
按新规则的意图，这些都得换成「查法」而不是「值」——**否则下一个接手的人
照抄一次，这个坑就重演一次**，而这正是它被写进红线的原因。

改成：

```
user.name  = 你自己的用户名
user.email = <自己的数字ID>+<用户名>@users.noreply.github.com
数字 ID 用 gh api users/<用户名> --jq .id 查
```

**刻意不写任何具体身份**，包括本机操作者自己的。`AGENTS.md` 第六节已经是查法的
权威出处，文档里不必再复述值。

## 关键决策与取舍

- **只清理「身份值」，不清理「人名」**。`docs/agent-memory.md` 与
  `docs/worklog/2026-09-28-git-identity-rule.md` 里提到成员用户名的地方是**叙述**
  （「Windows 侧成员的前三个提交被记到了所有者名下」），不是可照抄的配置，
  删掉反而让事故记录变得不可理解，所以不动它们。判别标准很简单：
  **能不能被直接粘进 `git config`**。
- **不改写历史**。这次的修正是新增一个提交，而不是再改一次已合并进 `main` 的提交 ——
  分支保护已开，且 `main` 上的提交不该为了文案而重写。
- **待办清单做的是「删除 + 重编号」，不是打勾**。`HANDOVER.md` 的读者是下一个接手的人，
  一份混着已完成项的清单只会让他重新判断哪些还成立。删掉「评审合并 PR #2」与
  「`main` 尚未设分支保护」两项（都已由 #2 / #4 完成），其余重新编号为 1–6；
  正文里指向待办的两处交叉引用（`第 6 节第 1 条`、`待办第 2 条`→`第 1 条`）同步改掉。

## 踩坑与排查过程

- 本地 `main` 落后 10 个提交这件事，**`git fetch` 的回显是靠不住的**（本机沙箱会吞掉
  git 写 ref 的动作，详见 `2026-09-28-merge-unix-support-on-windows.md`）。
  判断远端真相一律用 `git ls-remote --heads origin`；本次就是靠它才发现
  「分支被删了、`main` 前进了」。
- 同步本地 `main` 也得手工来：直接 `echo <sha> > .git/refs/heads/main`，
  然后 `git checkout main`（这一步只写 HEAD 与索引，是正常工作的）。
- 顺带发现：`docs/agent-memory.md` 里那条「`main` 已开分支保护」的记录写得挺细
  （含「不要求审批人数」「协作者都是 write 权限，开 PR / 合并无需等对方」），
  说明规则是有人**实际开了保护再回头记录的**，不是纸面约定。

  `smoke-test.js` / `browser-check.js`（它们测的是服务行为，与本改动无关）。
