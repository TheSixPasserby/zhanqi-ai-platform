# 将 README 补齐为后端架构、全部接口与数据库结构的可核对参考

- 日期：2026-10-26
- 作者：TheSixPasserby / Codex
- 分支 / PR：`codex/docs-backend-reference`，通过本分支 PR 合入 `main`

## 做了什么、为什么

用户要求 README 能说明后端如何运行、每个接口的作用和全部数据库结构。
旧稿仍写“约 60 个接口、11 张表”，并把手写游客 H5 说成 uni-app 构建产物；
所链接架构文档还把实际 JDBC 查询解释为常驻内存缓存。只往旧稿追加表格会继续传播错误的架构前提。

这次以当前 Controller、Service、Db/Tables、schema、初始化和鉴权实现为依据重写核心章节。
架构部分说明进程拓扑、各层职责、初始化依赖、令牌解析、请求链路、配置来源和交易状态。
数据库部分覆盖 12 张表的 140 个物理字段，以及全部主键、唯一/普通索引和逻辑关系。
接口部分按 9 个控制器逐项覆盖 77 个 HTTP 方法与路径组合，写清权限、输入、返回和副作用。

## 关键决策与取舍

- **所有核心内容都留在 README**，满足一个文件可查阅的需求；使用稳定目录锚点、表名跳转、
  模块导航分担篇幅，没有把“完整参考”藏到另一个文档里。
- **字段定义只集中维护在第五节**。接口章引用完整字典并解释序列号、JSON/金额转换和暴露范围，
  避免把类型/默认值复制到第二套数据定义中。
- **按当前行为记录，不替实现补写能力**：如商家头像/改密的 ID 问题、活动派生字段导致保存失败、
  PC 预约商品缺日期、注册响应只返回 ok、无分页、无统一事务和宽松状态校验，均明确标注。
  这次不顺手改业务代码，后续修复须同步文档和专项断言。
- **区分商品预约和活动报名**：前者写 orders、涉及商品库存和金额；后者写 activityBookings、
  占活动人数名额，不生成交易订单。
- 同步修正已链接的 `docs/架构说明.md` 缓存段，其他历史设计背景保留并指向 README 当前契约。
  uni-app 与静态 H5 发布边界也一并纠正，避免读者按旧说明覆盖新版页面。

## 踩坑与排查过程

- 按“带 Mapping 的方法”计数会得到 76；健康检查一个方法有两个显式路径，展开后才是 77 个路由。
  不把 Spring 隐式 HEAD/OPTIONS、静态转发或路径变量的具体值算成新接口。
- 直接全文数 `CREATE TABLE IF NOT EXISTS` 会把 SQL 注释中的说明也计入；必须定位真实建表语句，
  才能得到 12 张表。`Tables` 登记 128 个业务列，不包含各表 seq；物理字段是 140 个。
- 数据字典容易照抄注释“时间都是 VARCHAR、图片都是路径”，但 expiresAt 实际为 BIGINT，
  三个 avatar 实际为 TEXT dataURL；这些例外均在字段表中说明。
- 接口注解没有包含全部权限信息：两套 Admin 控制器使用类注解，商城和预约服务继续检查资源归属。
  schema 列出全部表并不表示通用 data 接口也允许操作全部表。
- 文档覆盖检查需要按“字段表”识别行；sessions 后的角色关系表同样使用反引号，
  若不限定 SQL 类型会误算字段数量。临时核对器已按类型和表章节边界识别。

## 遗留问题与下一步

README 第八节“当前限制”记录的是实现现状，不是已经修复。
后续应优先为新个人资料、活动编辑、电脑版预约结算补专项回归，并修复相应路径。
现有 97 项通过不能代表所有新增接口和边界条件都已覆盖。

涉及真实旧库升级时，还要解决固定种子 ID 冲突和删除后 ID 复用；文档没有把幂等 DDL
误写成可以自动处理全部迁移和数据一致性问题。
