# 修复 PC 聊天界面样式整体丢失 + 进入消息界面的偶发异常

- 日期：2026-10-29
- 作者：lead（DeepSeek Harness Team）

## 现象（用户报的）

用户截图上，电脑游客端进入聊天后：**消息没有气泡**（纯文字浮在背景上）、
**商家头像变成一个巨大的圆形图**、**输入框与发送按钮错位**、消息之间有大块不明空白。
同时反馈「新发送的消息后面还是有不明意义的空白」和「进入消息界面有可能会显示有问题」。

## 根因（不是偶发，是必现）

**`static/visitor/pc/pc.css` 被整块覆盖，丢了 150 个选择器。**

上一轮（PR #15）我为聊天输入框自适应追加 CSS 时，用 `write` 覆盖了整个文件。
当时的 `write` 内容基于一次较早的读取，而期间文件已被别的改动更新过 ——
覆盖后剩下的内容是「基线的一段 + 我追加的几行」，中间约 291 行（聊天、商家主页、
举报中心、购买面板、摄像头、画册脚本等全部样式）被整块抹掉。

因为 **CSS 缺失不会报 JS 错误、接口也全是 200**，页面「看起来能跑」，
所以我上一轮的 CDP 断言（量高度、量元素存在性）全部通过了 —— 它们量的是
「元素在不在」，而不是「样式有没有生效」。这是上一轮自检的真实盲区。

`static/visitor/css/visitor.css` 同时丢了 9 个选择器（举报结果、凭证行），也是同一原因。

## 修复

1. **从 `1c65f33`（本轮改动前的 main）取回两个 CSS 的完整基线**，
   再把我这两轮真正新增的规则（`.order-settle`/`.settle-row`、`.ring-empty`、
   聊天输入框限高、空消息隐藏）**追加回去**。没有手工重写，避免再次遗漏。
2. 用选择器集合做**集合差校验**：基线 590 + 462 个选择器，逐个确认「丢失 0」。
3. 顺带加固了「进入消息界面偶发异常」的第二个真实隐患：
   `openChat()` 切换商家时**没有清理上一个会话的残留状态**（消息、在线状态、
   商品列表），而且三个异步请求（`loadChatMessages`/`loadChatPeer`/`loadChatProducts`）
   **没有竞态保护** —— 快速连点不同会话时，先发的请求后回来会覆盖新会话的内容，
   表现为「进去看到的是上一个商家的消息」或「消息闪一下变了」。
   修法：加 `chatSendSeq` 会话代次，切换商家时 +1，所有异步回调回来先校验代次，
   不一致就丢弃。

## 自检盲区的补丁（本次最有价值的产出）

原来的 `browser-check` 只检查「元素存在 + 无 JS 异常 + 无 4xx」，抓不到 CSS 丢失。
新增第 5 组「聊天界面样式完整性」哨兵，**直接量渲染后的几何**：

- 气泡必须有非透明背景 + 内边距 ≥ 8px（CSS 丢失时是 `rgba(0,0,0,0)` 和 `0px`）
- 头像宽度必须在 (0, 40] 之间（丢失样式时会变成原图大小）
- 输入框高度必须在 [30, 130]（丢失样式时会塌成 0 或被撑坏）
- 不能有空白气泡

**并且做了反向验证**：故意把 `.msg-text` 的 padding 改成 0 重新打包，
确认哨兵报 `[FAIL] 消息气泡有背景与内边距` 且 exit=1 —— 证明它不是空断言。
这一步很关键：不加反向验证的话，新断言很可能只是「一直通过」的装饰。

`browser-check` 从 53 项 → **58 项**。

## 走过的死胡同

- 一开始怀疑是 8083 端口跑着旧实例（用户截图地址是 `10.189.104.162:8083`）。
  查下来 8083 已不在监听，8080 是本项目、8081 是无关项目、8082 是 QQ。
  旧实例确实存在过，但**根因是 CSS 丢文件**，不是多实例。
- 试过在页面内 `location.href` 跳转来做哨兵的前置登录，会被 PC 页的
  手机端检测改道到 `/visitor/`（拿到的是手机版，没有 `#pc`）。
  改用 CDP 的 `Page.navigate` + `sessionStorage.forceMobile=0` 才稳定。
- 探测脚本里用反斜杠 n 拼接多行消息，多层字符串转义后传给 `Runtime.evaluate`
  会 `SyntaxError`；改用 `String.fromCharCode(10)` 拼接。

## 自检结果

- `node tools/normalize-scripts.js --check`：通过
- `node tools/smoke-test.js 8080`：**158/158**
- `node tools/browser-check.js 8080`：**58/58**（含新增 5 项样式哨兵，已反向验证有效）
- 1024×768 实视口专项验收：**13/13**
  （进入气泡样式、头像 34px、容器高度、发送后气泡与时间间距 ≤6px、
   时间下方 ≤4px、输入框复位、刷新后历史无空消息、全程无异常/失败请求）
- 三个页面挂载回归：游客 PC / 商家 / 管理端均正常

## 教训（已写入 agent-memory）

**不要用 `write` 覆盖带大量既有内容的文件**。追加内容用 `edit` 定位插入，
或者读完整内容再整体写回。覆盖式写入一个 1200 行的 CSS 时，
只要读到的版本比磁盘旧，就会静默丢掉中间的整块内容，而且**没有任何报错**。

## 遗留问题

1. 多行气泡在极长文本（>500 字）下会撑得很高，目前靠 `chat-body` 滚动，
   没有折叠；演示够用，生产可考虑「展开全文」。
2. 样式哨兵只覆盖游客 PC 端聊天。商户端聊天（Element UI 的 `.chat-bubble`）
   未加同类断言，下次动商户端样式时建议补一组。
