## 一、总览

### 1.1 一句话定位

> **郫都区战旗村农商文旅智慧服务平台**：一台普通电脑当服务器，
> 后端一个 SpringBoot 进程 + 一个 MySQL 库，同时支撑**四个客户端**
> （PC 管理后台 / 商户工作台 / 游客端 H5 / 安卓 App），
> 用户双击一个 `.bat` 就能跑起来。

### 1.2 一句话讲清三个卖点（开场用）

| 卖点 | 一句话 | 证据 |
| --- | --- | --- |
| **双击即用** | 用户机器上只要装了 JDK 和 MySQL，双击 `一键部署.bat` 自动完成「探口令 → 建库 → 建表 → 灌数据 → 启动 → 打印四端地址」 | `DatabaseBootstrap.java` 全程无 `mysql` 客户端依赖 |
| **零构建前端** | 三端页面是原生 HTML + 全局 Vue2 + 本地 `vendors/`，**不需要 Node、不需要 npm install**，所以不存在「装不上依赖就部署不了」 | `static/*/index.html` 直接引 `../vendors/vue.min.js` |
| **AI 不编造** | 问答严格依托本地 16 条知识库：**检索不中就直接说「没找到」**，命中才交给大模型润色；大模型挂掉自动回落本地原文，接口永远不报错 | `AiService.ask()` |

### 1.3 技术栈与规模

| 层 | 技术 | 说明 |
| --- | --- | --- |
| 后端 | SpringBoot 3.3.5 + Java 17 + Spring JDBC + HikariCP | 单进程、单 fat jar、内嵌 Tomcat |
| 数据库 | MySQL 8/9（实测 9.6） | 11 张表，`utf8mb4` |
| PC 后台 | Vue 2.7.16 + Element UI 2.15 | 零构建，依赖已内置 `static/vendors/` |
| 商户工作台 | 同上 | 零构建 H5 |
| 游客端 H5 | 同上（**手写 Vue2，非构建产物**，见 §6.3） | 零构建 |
| 安卓 App | uni-app（Vue 3 + Vite）源码工程 `uniapp-visitor/` | 仅打包 App 时用，需要 Node |
| 图表 | **手写 SVG 的 Vue 组件** | `assets/js/charts.js`，无 ECharts/Chart.js |
| 自检 | Node 脚本 3 个 + 编码校验 1 个 | 全部零 npm 依赖、可离线跑 |

### 2.2 后端分层职责（讲的时候逐层点名）

| 层 | 包 | 职责 | 铁律 |
| --- | --- | --- | --- |
| **契约层** | `common/` | `R` 出统一响应、`ApiException` 表达业务异常、`GlobalExceptionHandler` 兜底、`Dict` 管枚举中文、`Json` 管序列化 | 响应永远是 `{ok:true,…}` / `{ok:false,error:"中文"}`，`error` 可直接弹给用户 |
| **鉴权层** | `auth/` | `Accounts` 管三类账号、`AuthService` 管会话与登录、`AuthInterceptor` + `@RequireRole` 做接口门禁、`AuthContext` 用 ThreadLocal 传当前用户 | 拦截器**默认放行**，权限靠注解显式声明（见 §6.1 —— 这是 P0 的根因） |
| **数据层** | `db/` | `Db` 是唯一门面、`Tables` 是表/列白名单、`DatabaseBootstrap` 负责幂等自举 | 业务层不出现一行 SQL；所有查询 `ORDER BY seq` |
| **接口层** | `controller/` | 9 个控制器，只做「取参数 → 调 service → `R.ok()`」 | 不写业务规则 |
| **业务层** | `service/` | 8 个服务，业务规则集中地 | 不碰 SQL、不碰 HTTP |
| **基础设施** | `config/` | `PortGuard` 锁端口、`WebConfig` 挂拦截器 + CORS + 静态托管、`DataSourceConfig` 建连接池、`AppProperties` 绑配置 | 端口一律从 `portGuard.getPort()` 取 |

### 2.3 依赖方向（单一方向，无环）

```
controller ──► service ──► db ──► JdbcTemplate ──► MySQL
     │            │         ▲
     └──► common ◄┘         │
          auth ─────────────┘   （AuthService 依赖 Db；AdminService 依赖 Accounts+AuthService）
```

- `Db` 的构造函数**刻意接收 `DatabaseBootstrap`**（`Db.java:32`），
  用构造依赖把「建库建表」强制排在「第一次查询」之前 —— 一个用 IoC 表达时序的技巧。
- 只有 `ServerService` 例外地直接注入 `JdbcTemplate`（`ServerService.java:54`），
  用于读表结构元数据（`information_schema`），这是唯一绕过门面的地方。

### 2.4 四端与后端的边界（一条硬约束）

**游客端与商户端不允许出现服务器地址。** 实现方式分两种：

| 客户端 | 怎么找到后端 |
| --- | --- |
| H5 三端 | 与接口**同源**，请求走相对路径（`assets/js/api.js` 默认 `base=''`） |
| 安卓 App | 首启扫码/手填，地址存在手机本地（`uniapp-visitor/src/api/store.js` 的 `zhanqi.baseUrl`） |

地址的**定义权**在 PC 后台的 `settings` 表（`link.*` 键，`ServerService.links()` 组装），
App 只是把它读回来。这条边界让「换台电脑当服务器」不需要改任何前端代码。

### 2.5 跨层约定（讲课时值得单独强调的四条）

1. **响应格式统一**：`R.ok(...)` / `R.err(...)`（`R.java:19,27`），前端只判 `ok`。
2. **每张表都有 `seq BIGINT AUTO_INCREMENT`**，所有查询 `ORDER BY seq`（`Db.java:40`）——
   MySQL 不保证返回顺序，「最近 N 笔」这类逻辑必须靠它。
3. **时间字段一律 `VARCHAR`**（种子数据里既有 `2026-10-01` 也有 ISO 串，用 `DATETIME` 要反复转换）。
4. **SQL 脚本必须幂等**：`schema.sql` 全 `CREATE TABLE IF NOT EXISTS`、`seed.sql` 全 `INSERT IGNORE`。

## 四、关键流程与调用链路

### 4.1 启动链（最能体现「双击即用」的一条，建议重点讲）

```
双击 一键部署.bat
  └─► tools/deploy.ps1 start
        ├─ Assert-Java     找 JDK（JAVA_HOME → PATH → 常见安装目录）
        ├─ Assert-MySql    用 Get-ConfigValue(...,'database') 读配置，TCP 探活
        ├─ 选端口           命令行 > ZQ_PORT > 找空闲（8080→8119）
        ├─ Write-LocalConfig 写 config/application.yml
        └─ Start-Process java -jar dist/zhanqi-cloud-server.jar
              └─► Spring Boot 启动
                    ├─ PortGuard.customize()      容器创建前锁端口（拦截 SERVER_PORT 劫持）
                    ├─ DatabaseBootstrap.init()   ①建库 ②schema.sql ③seed.sql ④打摘要
                    └─ Db 构造（依赖 Bootstrap，保证表已就绪）
        └─► Wait-Health 轮询 /api/health → Show-Banner 打印四端地址
```

**讲点**：为什么必须用 `PortGuard`？因为环境变量优先级高于 `application.yml`，
一旦运行环境预置了 `SERVER_PORT`，配置写 8080 也会被绑到随机端口，
表现是「各端页面全打不开且无报错」（`PortGuard.java:16-21` 记了这次真实事故）。

### 4.2 登录链（含最严重的那个安全问题）

```
密码登录：
POST /api/auth/login {account,password,client,expect}
  └─ AuthService.login() 139
       ├─ 按 merchant → admin → buyer 顺序在对应表里找账号
       ├─ 账号不存在与密码错误返回同一句话（防枚举）           ← 安全设计
       ├─ 校验 expect（角色走错端给明确提示，而不是登录后满屏 403）
       ├─ createSession()  生成 32 位十六进制 token 存 sessions 表
       └─ 首次登录下发 rememberToken，并把 loginCount +1      ← 为「快捷登录」铺路

快捷登录（免密）：
POST /api/auth/quick-login {account, token}
  └─ AuthService.quickLogin() 186
       └─ 三条件同时满足才放行：loginCount>0 + rememberToken 非空 + 令牌匹配

每次请求：
AuthInterceptor.preHandle()
  ├─ AuthService.resolve(request)  读 token → 查 sessions → 校验过期 → 查账号 → 校验未停用
  │    └─ 账号被停用/删除 → 会话立即失效（管理员「停用」能即时踢人）
  ├─ AuthContext.set(me)           ThreadLocal，供 service 取当前用户
  └─ 有 @RequireRole → 校验角色；没有 → 直接放行      ← ⚠️ P0 根因，见 §6.1
```

### 4.3 下单链（业务最复杂，讲库存一致性）

```
POST /api/shop/orders {items:[{productId,qty}], bookDate, people, address}
  └─ ShopService.createOrders() 175
       for 每个 item:
         ├─ 查商品，校验在售            → 失败则记入 warnings，continue
         ├─ 校验库存 stock >= qty       → 同上
         ├─ 预约类必须带日期 / 实物类必须带地址（服务端兜底校验）
         ├─ db.insert("orders")        ① 插订单
         └─ db.update("products")      ② 扣库存 + 加销量
       至少成功一笔则返回 {orders, warnings}；全失败则 400
```

**讲点与风险**：①②之间**没有事务**（全项目 0 处 `@Transactional`），
进程崩溃或并发下单会造成「订单在但库存没扣」或丢失更新。演示规模可用，
但这是从演示走向生产的第一个要改的点。

### 4.4 AI 问答链（防幻觉设计，讲课时最有说服力）

```
POST /api/ai/ask {question}
  └─ AiService.ask() 189
       ├─ 打招呼短路（正则 + 长度 ≤6）
       ├─ retrieve(q,4)：全表打分 → 阈值 ≥8 才算命中
       │     打分 = 标签命中×10 + 标题二元重叠×3 + 正文二元重叠×0.8 + 单字×0.5
       ├─ 未命中 → 直接回「本地知识库没找到」+ 可问范围        ← 防幻觉关键
       ├─ 命中且已配大模型 → askLlm(systemPrompt, 知识库原文+问题)
       │     └─ 任何异常返回 null → 自动回落本地原文
       └─ 返回 {answer, sources[...], matched, similarity, engine}
```

**讲点**：`sources` 会作为「知识库来源标签」显示在回答下方 ——
答案有没有出处，用户一眼可见。这是「不训练自有大模型、只用知识库约束回答」
这条需求最直接的落地方式。

### 4.5 前端请求链（三端共用一套封装）

```
页面调用 window.ZQ.get('/api/tour/spots')
  └─ assets/js/api.js
       ├─ 拼 Authorization: Bearer <localStorage[zhanqi.<ns>.token]>
       ├─ 非 JSON 响应兜底 → 返回 {ok:false, error:'服务返回异常'}
       ├─ 401 → 清本地登录态 + 触发 onUnauthorized（各端注册：退回登录页）
       ├─ 网络异常 → 返回 {ok:false, error:'网络异常…'}（不会 unhandled rejection）
       └─ ok=false 且有 error → 触发 onToast（各端用 ElementUI $message 展示）
```

**讲点**：**只有一份**请求封装（`assets/js/api.js`，暴露 `window.ZQ`），
三端各自只用一次 `ZQ.notify.onToast/onUnauthorized` 注册自己的提示方式。
登录态按端命名空间隔离（`zhanqi.admin.token` / `.merchant.` / `.visitor.`），
解决「同一浏览器先登游客端再登后台会把前一个顶掉」的问题。

### 4.6 数据流特征（一句话总结）

**没有缓存层、没有 ORM、没有消息队列。** 每次请求都：`controller → service → Db → MySQL`，
`Db` 每次真实查库（`Db.java:29` 只有一个 `JdbcTemplate` 字段，无任何缓存）。
优点是链路极短、易读、易调试；代价是每次列表都是全表加载 + 逐行补字段（见 §6.2-10 的 N+1）。

## 五、关键设计模式与取舍

| 模式 | 落地点 | 为什么这么选 |
| --- | --- | --- |
| **表驱动白名单门面** | `Db` + `Tables`：表名/列名必须先在白名单登记，SQL 只在这一处生成 | 业务层零 SQL、零 ORM 噪音；表名与列名无法被注入（已验证：全项目唯一的原始 `where` 是固定串 + 绑定参数 `ShopService.java:51`） |
| **幂等自举** | `DatabaseBootstrap`：建库/建表/灌数据全部可重复执行 | 「双击即用」的前提；重复部署不报错、不覆盖已有数据 |
| **扩展点覆盖配置** | `PortGuard implements WebServerFactoryCustomizer` | 配置绑定阶段已无法挽救被环境变量劫持的端口，只能在容器创建前编程式写死 |
| **注解式鉴权 + ThreadLocal 传参** | `@RequireRole` + `AuthInterceptor` + `AuthContext` | 接口级声明、横切统一处理；但它「默认放行」的取向直接造成了 P0（§6.1） |
| **策略 / 降级兜底** | `AiService`：本地检索 ↔ 大模型润色，失败静默回落 | 演示现场断网、密钥过期都不能让页面报错 |
| **DTO 装饰器** | `decorateProduct()` / `decorateOrder()` / `toCard()` | 把「分类中文名、商家简称、状态文案」补齐在服务端，三端共用同一份结构，前端不重复映射 |
| **零构建前端 + 共享资产** | `static/assets/`（`api.js`/`charts.js`/`app.css`/`img`）三端共用 | 部署只依赖 JDK + MySQL，不会因某个 npm 包下载失败而部署不了 |
| **零依赖自检脚本族** | `smoke-test` / `browser-check` / `deploy-config-test` | 离线机器也要能跑；`browser-check` 走 CDP + Node 内置 WebSocket，跳过 puppeteer |
| **双平台脚本对等** | `deploy.ps1` ↔ `deploy.sh` 函数级对应 | 开发机可能是 macOS，部署机是 Windows；`AGENTS.md` 已固化为红线 |

**贯穿全项目的取舍**：所有选择都服从同一句话 ——
**「不出错」优先于「功能多」，面向会双击 `.bat` 的非技术用户。**

## 六、问题与风险汇总

> 严重程度定义：**P0** = 安全问题或数据错误，必须修；**P1** = 明确缺陷或与文档不符，建议尽快修；
> **P2** = 坏味道 / 可优化项，不影响当前演示。

### 6.1 P0：`/api/auth/known` 无鉴权泄露免密令牌 → 可免密登入任意账号（含管理员）

| 项 | 内容 |
| --- | --- |
| 位置 | `controller/AuthController.java:48-51`（接口无 `@RequireRole`）、`auth/AuthService.java:244`（把 `rememberToken` 放进响应）、`auth/AuthInterceptor.java:39-45`（无注解即放行）、`auth/AuthService.java:186`（凭该令牌免密换会话） |
| 影响 | 任何能访问该服务的人，**不需要任何凭据**即可拿到已登录过的账号的免密令牌，进而换取该账号的完整会话 —— 包括平台管理员 |
| 前置条件 | 目标账号成功登录过至少一次（`loginCount>0` 且 `rememberToken` 非空）。而 `README` 的演示流程恰恰要求「先手动登录一次」，所以在演示现场**必然成立** |
| 已实证 | 本地实例实测：`GET /api/auth/known`（无 Authorization 头）→ 返回含 `token` 的 admin 卡片 → `POST /api/auth/quick-login` → 拿到 `role=admin` 会话 → 该会话成功调用 `/api/auth/me` 与 admin 专属的 `/api/admin/data-overview`（读到 11 张表计数） |
| 建议修法 | ① 卡片里**不要回传**免密令牌，改为服务端下发一次性短票据；② 或把 `rememberToken` 换成不具免密能力的展示用 id，`quick-login` 改用「服务端签发的设备票据」；③ 至少给 `known` 加一道校验（如仅允许同源 / 限流 / 需要设备指纹）。**注意**：`quickLogin` 已经校验令牌匹配，问题不在校验强度，而在**令牌被公开接口白送** |
| 讲课提醒 | 如果现场演示「登录页不泄露账号」这个卖点，请**先修掉这条**，否则听众用浏览器地址栏就能拆掉这个卖点 |

### 6.4 值得肯定的地方（讲课时可用来平衡）

- **SQL 注入风险为零**：表名、列名必须过 `Tables` 白名单（`Db.quote()`/`column()`），
  全项目唯一的原始 `where` 是固定字符串 + 绑定参数（`ShopService.java:51`）。
- **防账号枚举做了两处**：登录失败统一话术（`AuthService.java:155-158`）、
  快捷登录列表只暴露登录过的账号（`AuthService.java:241`）。
- **「停用即踢下线」是真实生效的**：`resolve()` 每次请求都复查账号状态（`AuthService.java:123`）。
- **端口劫持防御有真实事故背书**，并把优先级规则写成了文档（`PortGuard.java:27-34`）。
- **自检体系是真的**：97 + 46 + 36 项断言零 npm 依赖；
  其中配置解析回归测试**从交付版脚本里抽函数体执行**，并且已反向验证「把它改坏后测试会红」。
- **每个坑都留了成因注释**：默认封面 `craft.jpg` → `craft.svg`（`ShopService.java:101-105`）、
  `port` 同名键（`deploy.ps1` 的 `Get-ConfigValue`）、bash 3.2 全角字符（`AGENTS.md`）。
  这种「注释解释为什么」的习惯在这个项目里是成体系的。
