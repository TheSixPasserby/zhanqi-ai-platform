# 战旗云 · 整体架构说明

> 本文档说明本平台的整体架构、模块划分、关键设计决策与数据流，供开发、答辩与二次开发参考。
> 面向「怎么用」的说明请看根目录 `README.md`；本文档面向「为什么这样设计」。

## 二、进程与部署拓扑

全项目**只有一个后端进程**，三端共用它。

```
                    ┌─────────────────────────────────────────────┐
   浏览器 / 手机     │  访问 http://<host>:<port>/  →  统一入口页    │
        │           └─────────────────────────────────────────────┘
        │
        │   ① /visitor/  游客端 H5（uni-app 构建产物）
        │   ② /merchant/ 商户工作台 H5
        │   ③ /admin/    PC 管理后台
        │   ④ /api/**    全部 REST 接口
        │   ⑤ /assets/** 三端共享的样式、脚本、插画
        ▼
   ┌──────────────────────────────────────────────────────────────┐
   │  SpringBoot 3.3.5（内嵌 Tomcat，单进程，默认端口 8080）        │
   │                                                              │
   │  ┌────────────────┐  ┌────────────────┐  ┌────────────────┐  │
   │  │ 静态资源托管    │  │ REST 控制器层   │  │ 局域网发现服务  │  │
   │  │ WebConfig      │  │ 9 个 Controller │  │ UDP 广播/应答   │  │
   │  └────────────────┘  └───────┬────────┘  └────────────────┘  │
   │                              │                               │
   │                      ┌───────▼────────┐                      │
   │                      │   Service 层    │                      │
   │                      │ 账号/点位/商城/  │                      │
   │                      │ 统计/AI/管理/设置│                      │
   │                      └───────┬────────┘                      │
   │                              │                               │
   │                      ┌───────▼────────┐   ┌───────────────┐  │
   │                      │  Db 数据访问门面 │   │  AiService    │──┼──► 第三方大模型 API
   │                      │  + Tables 元数据 │   │ 检索/润色/规划 │  │    (OpenAI 兼容)
   │                      └───────┬────────┘   └───────────────┘  │
   └──────────────────────────────┼───────────────────────────────┘
                                  │
                        ┌─────────▼──────────┐
                        │ MySQL zhanqi_cloud │
                        │ 11 张表 · utf8mb4  │
                        └────────────────────┘
```

**为什么做成单进程：**
部署复杂度是「不出错」的最大敌人。单进程意味着只有一个端口、一套配置、一份日志，
不存在跨域、不存在前端项目各自的服务地址配置、也不会出现「某个进程没起来导致页面空白」。
代价是不能独立扩容 —— 对课程演示与村级平台的实际规模，这个代价可以接受。

## 三、后端分层

```
controller/   收参、鉴权标注、组装响应       ← 薄，不含业务逻辑
    │
service/      业务规则、事务边界、数据组装    ← 业务都在这层
    │
db/           Db 门面 + Tables 表元数据       ← 屏蔽 SQL 细节
    │
MySQL
```

### 3.2 统一响应与错误处理

全站响应只有两种形态：

```json
{ "ok": true,  "products": [...] }        // 成功，业务字段平铺
{ "ok": false, "error": "库存不足，仅剩 2 袋" }  // 失败，error 可直接展示给用户
```

- 后端 `R.ok(...)` / `R.err(...)` 产出；`ApiException` 抛出的一切都会被 `GlobalExceptionHandler`
  转成 `{ ok:false, error }`，HTTP 状态码同时给出（400 / 401 / 403 / 404 / 500）。
- 前端**只判断 `ok` 字段**，不看状态码；`error` 直接弹提示。
  好处是：后端写的就是中文人话，前端不需要维护一张错误码映射表，也就不会出现「某个错误码没映射到，用户看到一串英文」。
- 未捕获的异常也会被兜住，返回一句中文并记日志，**任何情况下不回 HTML 错误页给前端**
  （`server.error.whitelabel.enabled: false`）。

### 3.3 数据访问层：为什么用内存缓存 + 写穿

`Db` 的实现是「启动时把整表读进内存 + 每次写入立刻同步到 MySQL（write-through）」。

选它的原因很实际：业务层的查询条件大量是 JS 断言函数
（例如「这个商家名下的、状态为在售的、按分类过滤的商品」），这类条件没法直接下推成 SQL。
演示规模下（几十到几百行），启动读进内存最简单，业务代码也最干净。

**代价与边界（如实说明）：**

- 启动时会把全部数据读入内存，数据量大了内存会顶不住；
- 写入是同步落库的，进程被强杀也不丢数据（已实测：改数据 → 强杀 → 重启 → 数据仍在）；
- **不能多实例同时跑**（两个实例会各写各的内存缓存）。

要支持多实例，需要把 `all / find / filter` 改写成真正的 SQL 查询，这是走向生产的第一项改造。

### 3.4 `PortGuard`：一个真实踩到的坑

**现象**：`application.yml` 里明明写着 `server.port: 8080`，启动日志却是
`Tomcat started on port 50995`，于是三端页面全部打不开，且没有任何报错。

**原因**：Spring Boot 的「宽松绑定」会把环境变量 `SERVER_PORT`（以及容器/沙箱环境常见的
`SERVER__PORT`）自动映射成 `server.port`，而**环境变量的优先级高于配置文件**。
本项目的开发环境恰好预置了 `SERVER__PORT=0`（0 = 随机端口），配置被静默覆盖。

**为什么「换个变量名」挡不住**：`server.port` 这个键本身就会被环境变量接管，
所以在 yml 里写 `${ZQ_PORT:8080}` 也没用 —— 覆盖发生在属性绑定的更上层。

**解法**：用编程方式在 Web 容器创建前把端口写死。
`PortGuard` 实现 `WebServerFactoryCustomizer`，其执行时机晚于配置绑定，能覆盖环境变量的影响：

```
优先级（高 → 低）：
  命令行 --server.port=9000   >   ZQ_PORT 环境变量   >   app.port 配置   >   8080
```

同时 `ServerService.getPort()` 也改为从 `PortGuard` 取，
保证**页面/二维码上展示的端口和实际监听的端口永远一致** ——
否则会出现「二维码里的地址扫不开」这种更难查的问题。

> 这是一个很好的例子：**配置文件写了不等于生效**。凡是「配置看起来对、行为却不对」的现象，
> 都要先怀疑是不是被环境变量或更高优先级的来源接管了。

## 四、三端前端架构

### 4.1 共同约定

三端共用一套设计语言：

| 令牌 | 值 | 用途 |
| --- | --- | --- |
| `--brand` | `#146B57` 竹青 | 主色 |
| `--brand-2` | `#1D9E75` | 主色亮部 |
| `--accent` | `#BE5230` 陶土朱 | 强调、印章、价格 |
| `--bg` | `#F6F4EF` 宣纸米白 | 底色 |
| `--text` / `--text-2` / `--text-3` | `#1F2A26` / `#5C6B65` / `#93A09A` | 三级文字 |

- `static/assets/css/app.css` 是 PC 后台与商户工作台共用的设计系统；
- 游客端因为跑在 uni-app 里（不支持 `:root` 变量），把同一套令牌写在 `App.vue` 的 `page` 选择器上；
- 三端的配色、圆角、阴影、状态标签语义完全一致，切换端不会有陌生感。

装饰性元素统一用**手写 SVG 插画 + 纯 CSS 动画**：
插画放在 `static/assets/img/`（林盘点位、农产、非遗等 13 张），
动画包括卡片错峰入场（`zq-rise`）、印章呼吸（`zq-breathe`）、骨架屏微光（`zq-skeleton`）、
AI 打字机光标（`zq-caret`）、波形跳动、扫描线等。

### 4.2 为什么 PC 后台与商户工作台选择「零构建」

Vue 2.7 + Element UI 的依赖文件直接放在 `static/vendors/`（本地文件，不走 CDN），
页面用全局 `Vue` 与 `ELEMENT` 写，不需要 webpack / vite，也不需要 `npm install`。

**收益**：一键部署只依赖 JDK + MySQL。用户不需要装 Node.js，
不会因为 npm 源慢、依赖冲突、磁盘空间不足而部署失败。

**代价**：没有单文件组件、没有热更新、不能用 `import` 语法；
代码组织靠约定（`admin.js` 按页面分块，`api.js` 统一请求封装）。
对本项目的规模（后台约 1600 行 JS，工作台约 800 行）是合适的。

> 如果后续要做成 SFC 工程，改动是局部的：把 `index.html` 里的模板抽成 `.vue`，
> 接口调用可以直接复用 `api.js` 的逻辑，后端一行都不用动。

### 4.3 游客端（uni-app）架构

```
uniapp-visitor/src/
├─ main.js           createSSRApp 固定写法（不能自己 mount，否则两端白屏）
├─ App.vue           全局设计系统（CSS 变量写在 page 上）+ 启动时准备连接地址
├─ pages.json        13 个页面 + 4 个 TabBar 页
├─ manifest.json     App 权限（相机/扫码）、H5 base=/visitor/、各端配置
├─ api/
│  ├─ store.js       登录态 + 服务器地址（按平台分支）
│  └─ index.js       请求封装 + 全部业务接口
├─ utils/
│  ├─ format.js      金额 / 时间 / 相对时间 / 业务字典
│  ├─ asset.js       后端相对路径图片 → 当前平台可访问的完整地址
│  ├─ cart.js        购物车（本地存储，按账号隔离）
│  └─ speech.js      语音讲解（H5 真朗读，App 回落文稿）
├─ components/       nav-bar（自定义导航栏）、empty-state（空/加载/错误三合一）
└─ pages/            13 个页面
```

**图片地址的跨端处理**（`utils/asset.js`）：
后端存的是相对路径（如 `/assets/img/spot-rice.svg`），这样同一份数据在四端都能显示。
`assetUrl()` 负责按平台还原：

- H5：页面与图片同源，直接用相对路径；
- App：拼上本机保存的服务器地址。

**服务器地址的分平台策略**（`api/store.js`）：

| 平台 | 地址来源 | 是否需要用户操作 |
| --- | --- | --- |
| H5 | 与接口同源，请求走相对路径 | 完全不需要 |
| 安卓 App | 本机存储（首次由扫 PC 后台二维码写入） | 首次扫一次码 |

这样满足了需求「其他端的连接配置统一在 PC 管理后台」：
**地址的定义权在后台，客户端只负责读回来，源码里没有任何硬编码 IP。**

**构建配置要点**：

- `vite.config.js` 的 `base: '/visitor/'` 与 `manifest.json` 的 `h5.router.base` 必须一致，
  否则 H5 的静态资源会 404；
- `manifest.json` 里声明了 `CAMERA` 权限与 `Barcode` 模块，供 App 扫码连接使用；
- `src/uni.scss` 刻意保持为空壳 —— **不引入 sass 依赖**，装依赖时就不会因为要编译 sass 而失败。

## 五、AI 引擎设计

```
用户提问
   │
   ▼
┌──────────────────────────┐
│ 1. 中文轻量检索           │  二元切分 + 标签/标题/正文加权打分
│    从 16 条村内知识库召回  │  命中 → 拿到条目 + 相似度
└───────────┬──────────────┘
            │
      ┌─────▼─────┐
      │ 命中了吗？ │
      └─────┬─────┘
      否    │    是
   ┌────────▼──┐  ┌──────────────────────────────┐
   │ 明确回答   │  │ enabled && baseUrl && apiKey? │
   │「知识库里  │  └──────────┬───────────────────┘
   │ 没有」     │        否    │    是
   └───────────┘  ┌──────────▼──┐  ┌─────────────────────────────┐
                  │ 直接返回知识 │  │ 把召回内容作为上下文交给大模型 │
                  │ 库原文+来源  │  │ 润色（受系统提示词约束）        │
                  └─────────────┘  └──────────┬──────────────────┘
                                              │ 调用失败
                                     ┌────────▼────────┐
                                     │ catch → 回落本地 │
                                     │ 知识库，不报错    │
                                     └─────────────────┘
```

**三个关键点：**

1. **单开关判定**：`enabled && baseUrl && apiKey` 三者齐备才走大模型。
   配置不完整不是错误状态，而是「本地模式」，页面照常用。
2. **失败必回落**：所有大模型调用都包了 try/catch，失败时静默使用本地知识库结果。
   用户看到的只是「回答来自本地知识库」，不会看到任何异常。
3. **防幻觉三道闸**：系统提示词约束 + 来源标签外显 + 未命中直接拒绝回答。

**行程规划**是纯本地算法（不消耗大模型额度）：
偏好关键词映射到点位 id → 按「上午 / 午餐 / 下午 / 晚间」时段编排时间轴 →
按在售的预约类项目价格与住宿均价折算预估花费。
这样即使完全没配大模型，行程规划也能给出完整可用的结果。

## 六、关键数据流

### 6.1 一键部署

```
双击 一键部署.bat（纯 ASCII + CRLF）
   │
   ▼
tools/deploy.ps1 start
   ├─ 找 JDK 17+           找不到 → 给出下载链接与安装要点
   ├─ TCP 探测 MySQL        连不上 → 给出三种启动 MySQL 的方法
   ├─ 找空闲端口（8080 起）  被占用 → 自动往后找并如实打印
   ├─ 写 config/application.yml（沿用已保存的口令）
   ├─ Start-Process java -jar dist\...jar --server.port=<端口>
   │    工作目录 = 项目根目录（Spring Boot 从 ./config 读本机配置）
   ├─ 轮询 /api/health（最长 90 秒）
   │    失败且日志含「数据库连接失败」→ 交互式索要 MySQL 口令 → 重新配置并启动
   ├─ 调 /api/server/info 拿真实局域网地址（避开虚拟网卡）
   ├─ 打印四组访问地址 + 默认账号 + 数据库摘要
   └─ 打开浏览器
```

启动后，服务端 `DatabaseBootstrap` 自己完成：

```
① 不带库名连 MySQL，CREATE DATABASE IF NOT EXISTS zhanqi_cloud
② 执行 db/schema.sql（全部 CREATE TABLE IF NOT EXISTS，只补缺失的表）
③ 执行 db/seed.sql（全部 INSERT IGNORE，已有数据不覆盖）
④ 打印一行连接摘要（端口 / 库名 / 各表记录数）
```

口令探测：先试配置里的口令，不通就依次试 `""`, `root`, `123456`, `12345678`, `1234`, … 共 10 个常见口令。
试通后写回配置对象供连接池使用。**全部不通才在部署脚本里问用户**。

整个链路不需要 `mysql` 命令行客户端，也不需要用户手工执行任何 SQL。

### 6.2 打卡集章

```
点「立即打卡」
   → POST /api/tour/spots/{id}/checkin   [角色: buyer]
   → TourService.checkin()
       查 (userId, spotId) 是否已有记录
         有 → 返回 repeated=true + 友好提示（不报错）
         无 → 写入 stamps 记录（数据库唯一键兜底）
              → 统计已集章数与总数，返回 allDone
   → 前端局部更新该卡片状态 + 震动反馈 + Toast
```

重复打卡「不报错、给友好提示」是刻意的交互选择：用户点两次是常见行为，
报错会让人以为坏了。数据库层的 `(userId, spotId)` 唯一键保证并发下也不会产生重复印章。

### 6.3 下单 / 预约

```
POST /api/shop/orders  [角色: buyer]
body: { items:[{productId, qty}], bookDate, people, address, remark }

ShopService.createOrders() 逐件处理：
   商品不存在或已下架      → errors += "xxx 已下架"
   库存不足               → errors += "「xxx」库存不足，仅剩 N 袋"
   预约类没选日期          → errors += "「xxx」需要选择预约日期"
   通过 → 建订单（status=pending）+ 扣库存 + 加销量
   全部失败 → 400，返回 errors
   部分成功 → 200，created + warnings 一起返回

前端：有 warnings 就如实展示，不假装全部成功。
```

「能下的先下、不能下的收集原因」这个设计避免了「一件商品缺货导致整单失败」，
也让用户清楚知道哪件没下成。

订单状态流转：`pending 待确认 → confirmed 已确认 → used 已核销`，
任意阶段可 `cancelled 已取消`（取消时回滚库存，并记录 `cancelledBy`）。

## 七、稳定性设计清单

「以不出错为核心」不是口号，落实成了下面这些具体做法：

### 7.1 部署期

| 风险 | 做法 |
| --- | --- |
| 用户没装 JDK | 启动前主动检测版本，给出下载链接与「记得勾选 PATH」的提示 |
| MySQL 没启动 | 先做 TCP 探测，给出三种启动方法（服务管理器 / phpStudy / 改端口） |
| 不知道 MySQL 口令 | 服务端自动探测 10 个常见口令；仍失败则部署脚本交互式询问一次，写回配置 |
| 端口被占用 | 从 8080 起自动往后找空闲端口，并如实打印最终端口 |
| `.bat` 一闪而过 | `.bat` 强制 CRLF + 纯 ASCII；所有中文提示交给 PowerShell 打印；`tools/normalize-scripts.js` 可自检与自动修复 |
| `.ps1` 中文乱码 / 语法错 | `.ps1` 强制 UTF-8 **带 BOM**（PowerShell 5.1 没 BOM 会按 GBK 读，中文里恰好含单引号字节时会截断字符串，报出看起来像参数错误的诡异信息） |
| 脚本输出丢失 | 脚本内自己落一份日志到 `logs/deploy-console.log`（用外部管道取输出时，脚本里的 `exit` 会让管道来不及 flush，拿到的是上一次的旧日志） |
| 服务窗口被关掉 | 服务用 `Start-Process -WindowStyle Hidden` 后台运行，关掉黑窗口不影响服务 |
| 重复部署 | 建库/建表/灌数据全部幂等；重复双击只会重启服务 |

### 7.2 运行期

| 风险 | 做法 |
| --- | --- |
| 环境变量劫持端口 | `PortGuard` 编程式锁定端口；页面展示的端口与实际监听端口同源 |
| MySQL 挂了 | `DatabaseBootstrap` 用人话打印排错步骤，不是抛一堆堆栈了事 |
| 大模型调用失败 | try/catch 回落本地知识库，用户无感 |
| 大模型乱答 | 知识库约束 + 来源标签外显 + 未命中拒绝回答 |
| 手机连不上 | 网卡列表标注虚拟网卡、自动挑物理网卡；二维码内容即手机端地址 |
| 时间格式混杂 | 统一用 `VARCHAR` 原样保存，避免 DATETIME 的时区/毫秒/Z 后缀转换坑 |
| 查询顺序不稳定 | 每张表都有 `seq BIGINT AUTO_INCREMENT` 写入顺序号 |
| 前端拿到非 JSON | 前端兜底把非 JSON 响应转成 `{ok:false,error:"服务返回格式异常"}`，页面不会因解析失败白屏 |
| 登录过期 | 401 统一处理：清本地会话 + 提示 + 跳登录页（带防重复跳转） |
| 图片 404 | `assetUrl` 按分类给兜底插画，不出现破图 |
| 重复打卡 | 数据库唯一键 + 业务层友好提示 |

### 7.3 编码与文件约定

| 文件类型 | 强制约定 | 原因 |
| --- | --- | --- |
| `.bat` / `.cmd` | CRLF + 100% ASCII | cmd 按字节解析，中文会让 `chcp 65001` 后的行被截断 |
| `.ps1` | UTF-8 **带 BOM** + CRLF | PowerShell 5.1 无 BOM 时按 ANSI 读，中文乱码且可能破坏语法 |
| `.sql` / `.java` / 前端源码 | UTF-8 无 BOM | 通用约定 |
| 源码中的标识符 | 一律 ASCII 直引号 | 避免全角引号导致的语法错误 |

自检命令：`node tools/normalize-scripts.js --check`（可挂到提交前钩子或 CI）。

## 九、自动化验证与实测记录

本项目不接受「接口返回 200 就算通过」。两套自检脚本 + 一轮人工跑通，才算完成。

### 9.1 两套自检脚本

| 脚本 | 覆盖 | 依赖 |
| --- | --- | --- |
| `node tools/smoke-test.js` | 97 项接口断言 + 1 项静态检查。含认证与角色权限矩阵、打卡幂等、下单与库存回滚、AI 问答命中与未命中、后台管理接口、服务器管理接口 | 无（只用 Node 内置模块） |
| `node tools/browser-check.js` | 46 项前端断言。四端页面真实渲染、关键 DOM 存在性、整轮交互（注册→登录→打卡→加购→下单→AI 问答→行程规划）无异常、无失败请求 | 本机 Chrome，通过 CDP 驱动，**不依赖 npm 包** |

浏览器自检能做到零依赖，是因为走 Chrome DevTools Protocol + Node 22 内置的 `WebSocket` 直连，
跳过了 puppeteer 这类需要联网安装的库 —— 在离线或 npm 不可用的环境里，这一点非常关键。

### 9.2 实测结论

```text
接口冒烟测试 ： 通过 97 项，失败 0 项
前端实机检查 ： 通过 46 项，失败 0 项
截图归档     ： docs/screenshots/（16 张，四端界面实拍）
```

### 9.3 验证过程中真实抓到并修掉的缺陷

这一节故意写得很具体 —— 它们都是「接口返回正常、界面看着也没报错」的隐蔽问题，
正是靠上面两套脚本才暴露出来的。

| # | 现象 | 根因 | 修复 |
| --- | --- | --- | --- |
| 1 | 三端页面全部打不开，启动日志显示 `Tomcat started on port 50995` | 运行环境预置了环境变量 `SERVER__PORT=0`，Spring 的宽松绑定把它映射成 `server.port`，而**环境变量优先级高于配置文件**，配置里的 8080 被静默覆盖 | 新增 `config/PortGuard.java`，用编程方式在容器创建前锁定端口；`ServerService` 也从它取端口，保证「页面上显示的端口」与「实际监听的端口」一致 |
| 2 | 商品列表出现裂图，控制台一条不起眼的 404 `/assets/img/craft.jpg` | 后端给「未上传封面的商品」写的默认路径是 `craft.jpg`，而目录里实际文件是 `craft.svg` | 抽出常量 `DEFAULT_COVER` 改正；并在 `smoke-test.js` 里加了一条静态检查，扫描全项目 13 处图片引用是否都有对应文件 |
| 3 | 游客端的「快捷登录」里出现 **admin 账号** | `/api/auth/known` 不区分角色，三类账号一起返回 | 接口加 `role` 参数，三端各传各的角色；游客端只可能拿到买家账号 |
| 4 | 浏览器里留着过期令牌时，打开页面连打 4 个注定 401 的请求 | 启动时只看本地有没有 token 就直接拉业务数据 | 新增 `verifySession()`：先用 `/api/auth/me` 确认令牌有效，无效就干净地退回登录页 |
| 5 | `rebuild.bat` 复制 jar 明明失败了，却照样打印「编译完成」 | `Copy-Item` 的失败没有被检查，`='Continue'` 让它静默通过 | 复制失败即致命退出，并校验源/目标文件大小一致；同时校验产物时间晚于本次编译开始时间，避免把上次的旧包当新包发出去 |
| 6 | 编译报 `Unable to rename ... .jar to .jar.original`，看不出真正原因 | 正在运行的服务占着 jar 文件 | 编译前用 `logs/server.pid` 检测并停掉在跑的服务；**并且校验该 PID 确实是 java 进程** —— 进程退出后 PID 会被系统回收给别人，只按 PID 判断会误杀无关程序 |
| 7 | `一键部署.bat` 打印的手机端地址是 `192.168.20.1`，手机根本连不上 | 脚本自己挑网卡，挑中了 VMware 的虚拟网卡 | 改为调用运行中服务的 `/api/server/info` 取地址 —— 服务端有一整套虚拟网卡识别与打分规则，且 PC 后台的二维码用的也是它，两边必须同源 |
| 8 | 同一浏览器里先登游客端、再登管理后台，前一个会被顶掉 | 三端同域，`localStorage` 的 key 相同，后一次登录覆盖前一次的令牌 | 登录态按端命名空间隔离（`zhanqi.admin.token` / `.merchant.` / `.visitor.`） |
| 9 | 实测「初始登录页不展示任何账号」失败 | 数据库里已有测试过程中登录过的账号 | 恢复干净数据（各账号 `loginCount` 归零、清空会话），并在自检脚本的失败提示里说明这是运行痕迹而非代码问题 |
| 10 | 无头浏览器控制台出现 `Blocked call to navigator.vibrate` | 浏览器规定振动只能在用户手势后调用，程序化调用会被拒绝并留一条 error | 调用前判断 `navigator.userActivation`；自检脚本同时把这类「浏览器自身的提示」列入白名单，避免报告长期带噪声 |
| 11 | 每个页面都有一条 `favicon.ico` 404 | 没有声明图标，浏览器按默认规则去请求 | 新增 `assets/img/favicon.svg`，四端页面显式声明 `<link rel="icon">` |

### 9.4 两条可复用的方法论

1. **「接口返回正常」不等于「界面正常」。** 前端最麻烦的是静默失败：模板引用了不存在的字段、
   某个接口 4xx 被 try/catch 吞掉、图片 404 —— 页面照样有内容，只是某一块是空的或破的。
   所以浏览器自检必须同时盯四件事：未捕获异常、控制台 error、**所有 ≥400 的请求**、关键 DOM 是否存在。
   实践下来，第三条抓到的问题最多。

2. **自检脚本自己也要保证不污染数据。** 脚本会注册测试账号、建测试商品、下单。
   账号和商品能删干净，但订单是交易凭证、后台刻意不开放删除，所以脚本如实改成「提示」而不是假装删成功。
   这类「测试残留」曾经咬过一次：几轮之前测试留下的订单里存着旧封面路径，
   后来改了默认封面之后，那些旧快照就变成了前台的一张破图，而且完全想不到是测试留下的。

## 十、性能与规模边界

| 维度 | 当前设计 | 说明 |
| --- | --- | --- |
| 数据量 | 演示级（几十到几百行/表） | `Db` 启动时整表读入内存 |
| 并发 | 单进程，无分布式锁 | 单实例足够支撑村级平台与课程演示 |
| 写入 | 写穿（每次立即落库） | 进程被强杀不丢数据 |
| 索引 | 主键 + 状态/分类/商家等常用查询列 | 当前查询走内存，索引主要为将来改 SQL 查询做准备 |
| 静态资源 | 由 SpringBoot 直接托管，关闭缓存 | 便于改完刷新即生效；生产可加缓存与 gzip |
